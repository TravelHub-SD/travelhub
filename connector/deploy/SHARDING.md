# تقسيم الموصّل: خدمة لكل خط طيران

الهدف: الخطوط الثلاثة تبحث **معاً** لا بالتناوب. صندوق Render المجاني
(٥١٢ ميجا) لا يتّسع لأكثر من متصفح واحد، فثلاث خدمات = ثلاثة متصفحات
متوازية = زمن بحث واحد بدل ثلاثة.

| | موصّل واحد | ثلاثة موصّلات |
|---|---|---|
| متصفحات متوازية | ١ | ٣ |
| زمن البحث الحيّ | ~٦٠ث (يلامس سقف Vercel) | **~٢٠ث** |
| الزحف الليلي | مسلسل | متوازٍ |

الكود يدعم هذا أصلاً: `SUDAN_CONNECTOR_URLS` تقبل روابط مفصولة بفاصلة،
والموقع يستعلمها كلها بـ `Promise.allSettled`.

> **لماذا لا نحتاج متغيّر `AIRLINE`:** `TTI_CARRIERS` هي التي تحدّد خطوط كل
> نسخة. أعطِ كل خدمة عنصراً واحداً فقط من المصفوفة، فتصير خدمة ذلك الخط.

---

## قبل أن تبدأ

افتح خدمة Render الحالية → **Environment**، وانسخ قيمة `TTI_CARRIERS`.
هي مصفوفة JSON بثلاثة عناصر، عنصر لكل خط:

```json
[{"name":"…","iata":"…","code":"…","login":"…","password":"…"}, …]
```

ستأخذ من هذه القيمة **عنصراً واحداً** لكل خدمة جديدة. لا تكتب بيانات
الدخول في أي ملف — تبقى في متغيّرات البيئة فقط.

---

## الخطوة ١ — أنشئ الخدمات الثلاث

ثلاثة حسابات Render منفصلة (بريد مختلف لكل حساب)، خدمة واحدة في كل حساب:

| الخدمة | الحساب |
|---|---|
| `tarco-connector` | الأول |
| `badr-connector` | الثاني |
| `sudanair-connector` | الثالث |

> **٧٥٠ ساعة مجانية لكل حساب.** بعد إصلاح الإيقاظ صار الزحف يوقظ الخدمة
> لمدّة عمله فقط (~٢٥ ساعة/شهر)، فحساب واحد يكفي الثلاثة نظرياً. الفصل
> على ثلاثة حسابات هامش أمان لحركة الزوار نهاراً.

لكل خدمة، **New → Web Service**:

| الحقل | القيمة |
|---|---|
| Repository | `TravelHub-SD/travelhub` |
| Branch | `main` |
| **Root Directory** | `connector` ← بدونها يفشل البناء |
| Runtime | Docker |
| Region | Frankfurt |
| Instance Type | Free |
| Auto-Deploy | Yes |

## الخطوة ٢ — متغيّرات البيئة

**مشتركة بين الخدمات الثلاث** (انسخها كما هي من الخدمة الحالية):

```
CONNECTOR_API_KEY
SUPABASE_URL
SUPABASE_SERVICE_KEY
KV_REST_API_URL
KV_REST_API_TOKEN
TTI_PORTAL_URL      = https://emea.ttinteractive.com/newUI/index.asp
SDG_PER_USD         = 3650
HEADLESS            = true
MOCK                = 0
BROWSER_CONCURRENCY = 1
```

**خاصّة بكل خدمة** — عنصر واحد من `TTI_CARRIERS` القديمة، بين قوسين مربّعين:

| الخدمة | `TTI_CARRIERS` |
|---|---|
| `tarco-connector` | `[ عنصر تاركو فقط ]` |
| `badr-connector` | `[ عنصر بدر فقط ]` |
| `sudanair-connector` | `[ عنصر سودانير فقط ]` |

> `CACHE_NAMESPACE` لا تضبطه: يُشتقّ تلقائياً من `code` الخط، فيصير لكل
> خدمة فضاء كاش وصفوف أسعار ومؤشّر زحف مستقلّ. الموقع يدمج الصفوف عند
> القراءة.

## الخطوة ٣ — تحقّق

لكل خدمة بعد اكتمال البناء:

```
https://<اسم-الخدمة>.onrender.com/health   →   {"ok":true}
```

## الخطوة ٤ — اربط الموقع والمجدوِل

**Vercel** → Settings → Environment Variables → `SUDAN_CONNECTOR_URLS`
(بفاصلة بينها، بلا `/` في الآخر) ثم **Redeploy**:

```
https://tarco-connector.onrender.com,https://badr-connector.onrender.com,https://sudanair-connector.onrender.com
```

**GitHub** → Settings → Secrets and variables → Actions → `CONNECTOR_URLS`
= نفس القيمة بالضبط.

> المجدوِل يبني وظيفة مستقلّة لكل رابط، فالثلاثة يزحفون بالتوازي. لا حاجة
> لتعديل ملف الـ workflow.

## الخطوة ٥ — أوقف الخدمة القديمة

بعد نجاح الثلاث، احذف الخدمة المدمجة (`travelhub-connector`) أو أوقفها —
وإلا ظلّت تستهلك ساعات وتكتب صفوفاً بفضاء اسم مختلف.

## الخطوة ٦ — امسح صفوف الخدمة القديمة ← لا تتخطّاها

صفوف الخزينة الحالية مكتوبة بالمصدر `3tair-badr-sudanair`. الخدمات الجديدة
تكتب بمصادر `3tair` و`badr` و`sudanair`، فيصير للمسار الواحد **أربعة** صفوف:
ثلاثة تتجدّد وواحد يتيم لا يحدّثه شيء.

والقارئ يشترط أن تكون كل الصفوف طازجة (حتى لا يُخفي خطاً)، فالصف اليتيم
بعد ٢٤ ساعة يدفع **كل** بحث إلى المتصفح — لأسبوع كامل، حتى يُعدّ مهجوراً.

فور نجاح الموصّلات الثلاثة، في Supabase → SQL Editor:

```sql
delete from flight_cache where source = '3tair-badr-sudanair';
delete from crawl_state  where id     = 'avail:3tair-badr-sudanair';
```

الصفوف تُعاد كتابتها من أول زحف — والبحث الحيّ يملؤها أثناء ذلك.

## تحذيران

- **لا UptimeRobot ولا أي مراقب إيقاظ.** هذا بالضبط ما أحرق ٢١٩٠ ساعة من
  أصل ٧٥٠ وعلّق الخدمات سابقاً. الخدمة تنام بعد ١٥ دقيقة خمول — والخزينة
  هي التي تغطّي بداية الاستيقاظ الباردة.
- **بداية باردة:** أول بحث بعد فترة هدوء يستغرق ٣٠-٦٠ث لأن الخدمة تستيقظ.
  المسارات المخزّنة لا تلمس الموصّل أصلاً فترجع فوراً.
